# DECISIONS

- **Modular monolith, plain PostgreSQL** – simple; no Supabase to avoid overlapping with the .NET backend.
- **.NET 9** – the version in use; upgrade to .NET 10 LTS is on the roadmap.
- **IMemoryCache first, Redis later** – add Redis only when running multiple instances.
- **PWA for desktop** – Tauri/Electron only if deep OS integration is needed.
- **ng-zorro-antd 22 (MIT), NOT PrimeNG** – PrimeNG was tried first in Phase 2 (user's choice) and dropped: PrimeNG 22 requires a PrimeUI license key (free Community tier, but needs registration; without a key it shows a red "Invalid PrimeUI License" badge, and its license forbids removing that mechanism). ng-zorro 22.2 is MIT, has no license check, and declares Angular `^22.0.0` peers. Always read the license terms of a UI library, not only its peer dependencies.
- **ng-zorro setup choices** – its stylesheets are NOT in the `styles` list of `angular.json` any more: the dark build and the light ("variable") build are copied as assets to `/themes/` and one of them is loaded at run time (see the themes decision below); static icon registration (`provideNzIcons`) in `core/ui.providers.ts`; `provideNzNoAnimation()` because `@angular/animations` is not installed; `NzModalService` and `NzContextMenuService` are not root-provided and are provided in `notes.routes.ts` (`NzMessageService` is root-provided). **`ng serve` does not reload `angular.json`: restart it after changing it** (it hid the KaTeX CSS from the user's dev server and from mine).
- **Own design tokens `--ink-*` in `src/styles/_tokens.scss`** – ng-zorro 22 exposes CSS variables only for primary/success/warning/error colors, not neutral ones.
- **Three themes: Light, Dark, Warm (chosen by the user), switched from a button in the sidebar** – `<html data-theme="light|dark|warm">` + design tokens defined per theme in `styles/_tokens.scss` (a new token must be defined in all three). The user fixed background and text colors: **Dark = Nord** (#2e3440 / #d8dee9), **Warm = Kanagawa Lotus** (#f1e9d2 / #4d699b), **Light** (#edeeec / #dc347f); every other color (surfaces, lines, accent, Markdown "special characters", code colors) was chosen and checked for contrast. Default Dark; the choice is saved in `localStorage` (`inknote.theme`). `core/theme.service.ts` applies it; a small script in `index.html` applies it BEFORE Angular starts (no wrong-color flash), so the two must be kept in sync.
- **Known contrast limit of the Light theme (user's choice)**: note text #dc347f on #edeeec is 3.73:1, below WCAG AA (4.5:1) for body text. Headings, links, code and the interface use darker variants (all >= 4.3:1). Comments in code are deliberately dimmer (~4:1) in all themes. Warm's text #4d699b on #f1e9d2 is 4.55:1; Dark's is 9.25:1.
- **ng-zorro cannot show two themes at once**: it ships a dark build and a light build (same selectors) and they cannot be loaded together. They are copied as assets (`/themes/ng-zorro-antd.{dark,variable}.min.css`), `ThemeService` swaps the `<link data-zorro>` (the new one is inserted right after the old one, i.e. BEFORE our own stylesheet, and the old one removed only when the new one has loaded). Light and Warm share the light build; only our tokens differ. Our `styles/_zorro-overrides.scss` restyles buttons, dialogs, menus, inputs, selects, toasts and the view switch with the tokens, in all themes.
- **Editor, code and diagrams follow the theme through CSS variables, no rebuild**: CodeMirror uses our own theme + `HighlightStyle` made of `var(--ink-syn-*)` (`markdown-editor/ink-editor-theme.ts`; `@codemirror/theme-one-dark` was removed, `@lezer/highlight` and `@codemirror/language` are direct dependencies); Shiki uses a "CSS variables" theme (`createCssVariablesTheme`, prefix `--ink-code-`) so code blocks recolor instantly; Mermaid has colors baked into its SVG, so it is re-initialized with its `base` theme fed by the computed CSS colors and the drawn-diagram cache is emptied when the theme changes. In Markdown the special characters (`#`, `*`, backticks, `>`, `-`, link brackets) have their own color (`--ink-syn-mark`).
- **Production build: `inlineCritical: false`** – Angular would inline only the default theme's tokens in `index.html`, so a user who chose Warm or Light would see a flash of dark colors on every load.
- **One sidebar, explorer style (chosen by the user)** – folders (notebooks) contain their notes; loose notes at the top level; tags below. Replaces the earlier navigation column + notes list. Needs ALL notes, so the sidebar loads the full list (summaries only) and groups/sorts/filters it on the client (`explorer-rows.ts`); the API's `?notebookId=` / `?tagId=` filters stay available but the UI does not use them. Inside a folder notes are sorted pinned first, then by TITLE (not by last edit: autosave would make the note under your cursor jump).
- **Actions in right-click menus plus a hover "..." button; no Save button, no trash icon in the editor (user's request)** – notes save by autosave and Ctrl+S (status in the footer). Deleting a note is in the note's menu in the sidebar, with a confirmation. The toolbar has two icons only: new note, new folder; tags are created from a "New tag…" row.
- **"Current folder"** = the last folder clicked, or the folder of the open note; "new note" and "new folder" use it. Open folders are remembered in `localStorage` (guarded with try/catch).
- **Name dialog takes the focus after one tick** – the modal moves focus to its own frame after opening; without the wait the input was never focused (found with a real browser, jsdom cannot show it).
- **Initial bundle budget: warning 1.2 MB, error 1.5 MB (raw)** – ng-zorro ships one 571 kB CSS file (~52 kB gzip); total transferred is ~186 kB.
- **Markdown pipeline: unified (remark/rehype) + KaTeX + Shiki + Mermaid, sanitized by DOMPurify** (Phase 3). All MIT (DOMPurify: MPL-2.0 OR Apache-2.0). Two XSS layers: remark drops raw HTML; DOMPurify cleans the final HTML (SVG/MathML allowed for KaTeX, `<annotation>` allowed, forms/style/button forbidden, links forced to `target=_blank rel="noopener noreferrer"`). `MarkdownPreviewComponent` sets `innerHTML` itself because Angular's sanitizer would strip the inline styles KaTeX/Shiki need; this is the only allowed place.
- **Shiki with explicit languages + JS regex engine** – 11 languages bundled and lazy-loaded; unknown fences fall back to plain text; no WASM. Add a language in `highlighter.ts`.
- **Mermaid loaded only when a note has a diagram** (dynamic import), `securityLevel: 'strict'`. Drawn diagrams are cached by source text (max 50, cloned DOM nodes, errors not cached) so unchanged diagrams are not redrawn after every keystroke pause.
- **Preview delay 50 ms via `PREVIEW_DELAY_MS` token** (was 150 ms): measured render takes 10-120 ms, so the wait dominated the perceived lag.
- **CodeMirror 6 wrapped by hand** (not a third-party Angular wrapper) – fewer dependencies, and the sync with the `value` model signal is ~10 lines.
- **Autosave: debounce 1.5 s via RxJS, delay injectable (`AUTOSAVE_DELAY_MS`)** – `exhaustMap` avoids overlapping saves; no autosave during a 409 conflict; the draft is also saved when switching notes or leaving the page; `beforeunload` warns when dirty. Limitation until Phase 7 (local-first): closing the browser inside the delay window can still lose a few seconds of typing.
- **`NotesStore.createNote` does not select the new note** – the editor still holds the previous note's draft and saves it before loading the new one.
- **npm `overrides` pins `katex` to the patched 0.19.1** – `rehype-katex`/`remark-math` depended on an older nested copy with a (low) advisory; `npm audit` is clean.
- **Store methods are `async` + `firstValueFrom`** – easier to read and test than `rxMethod` while learning; `rxMethod` can be adopted later for streams (e.g. search-as-you-type).
- **Container vs presentational components** – `NotesPageComponent` talks to the store; `NotesListComponent` only receives inputs.
- **State: Signals + SignalStore, RxJS for HTTP/streams** – RxJS is not used as a store.
- **EF Core 9.x (not 10)** – EF Core 10 requires .NET 10. Versions are pinned exactly in the csproj; `Microsoft.EntityFrameworkCore.Relational` is referenced directly so the test project resolves the same EF version as the API.
- **Guid v7 ids generated by the application** – lets offline clients create notes without ID clashes (Phase 7) and keeps index inserts ordered.
- **One shared `AppDbContext`, module folders inside one project** – simplest while learning; split into projects/DbContexts later only if needed.
- **Optimistic concurrency with `Version`** – update requests carry the last seen version; mismatch returns 409. Reused by sync in Phase 7.
- **Soft delete through an EF query filter** – rows stay (needed for sync); queries hide them automatically.
- **Dev DB on host port 5433** – a local Windows PostgreSQL service already uses 5432. Connection string lives in user-secrets.
- **Swagger UI (not Scalar) for API docs** – more familiar to the user. OpenAPI JSON is generated by .NET 9's built-in `AddOpenApi`; only the UI package `Swashbuckle.AspNetCore.SwaggerUI` is added.
- **Tests use real PostgreSQL via Testcontainers** – no mocked DbContext; real migrations are applied.
- **Phase 4: three modules (Notes, Notebooks, Tags) linked by Id + small contracts** – Note stores `NotebookId` and `NoteTag(NoteId, TagId)` rows (the join table belongs to Notes: a note's tags are part of its data). Modules talk only through `Contracts/` interfaces (`INotebookLookup`, `ITagLookup`, `INotebookUsage`); there are no cross-module navigation properties or queries. The one exception is the EF configuration, which names the other module's type to create the foreign key. The contracts point both ways (Notes -> Notebooks/Tags and Notebooks -> Notes) but never form a runtime cycle; if this grows, replace with domain events.
- **Notebook tree = flat table with `ParentId`; the API returns a flat list** – the client builds the tree. Moving a notebook rejects itself/descendants as the new parent (cycle check walks up the parents).
- **Deleting a notebook is refused (409) unless it has no sub-notebooks and no live notes** – no silent data loss. Notebook and Tag use hard delete for now (note: sync in Phase 7 may need tombstones). FK `notes.notebook_id` is `ON DELETE SET NULL` so soft-deleted notes never block it; `note_tags` rows cascade with their tag.
- **Organization (notebook, pin, tags) has its own endpoint `PUT /api/notes/{id}/organization`** – so editor autosave never overwrites it. It bumps `Version` (conflict detection) but not `UpdatedAt` ("updated" = content edited), so pinning does not reorder by date. Tag names are unique ignoring case via a `NormalizedName` unique index.
- **List order: pinned first, then `UpdatedAt` desc; filters `?notebookId=` and `?tagId=`** – a notebook filter matches exactly that notebook (not its sub-notebooks).
- **Phase 4 frontend: the tag filter lives in the URL** (`/notes?tag=<id>`) – survives reload, shareable, Back button works. Angular binds query params to the page's `tag` input (`withComponentInputBinding`) and passes it to the sidebar. Links that open/leave a note use `queryParamsHandling: 'preserve'`; creating a note drops it (the new note has no tags and would be hidden).
- **`OrganizationStore` (notebooks, tags) separate from `NotesStore`** – changes rarely, read by sidebar and editor. The notes page loads it; the editor only reads it.
- **Organization changes merge only version/notebook/pin/tags into `selected`** and the editor resets its text only when the SAVED text changes (`updatedAt` is part of the key). Otherwise the server's reply (last saved text) would overwrite an unsaved draft. While an organization request runs, `saving` is true so autosave and the pickers cannot race on the same version.
- **Notebook tree is built on the client** (`buildNotebookTree`, pure function) from the flat API list; drawn by a self-including `ng-template` (no recursive component).
- **Known limits (on purpose)**: moving a folder (change parent) has API support but no UI (no drag and drop either); tags are created in the sidebar only (not from the editor's picker); if an organization request fails, a picker may keep showing the value the user chose until the next reload; the sidebar is a fixed 18 rem (no resizing, no small-screen layout).
- **The first page load got lighter**: moving `NzModalService`/`NzContextMenuService` from the app-wide providers to the lazy notes route took the initial bundle from 1.18 MB (budget warning at 1.2 MB) to 1.00 MB raw. Lazy loading applies to providers too, not only to components. With the themes, ng-zorro's 590 kB stylesheet left the bundle (it is an asset loaded at run time), so the initial total is now ~444 kB raw / ~117 kB transferred.
- **Backend commands while the API runs locally** – a running API locks `bin/Debug`. Use `--configuration Release` for `dotnet test` and `dotnet dotnet-ef ...` (output goes to `bin/Release`) instead of stopping the API.
- **Note status** (`None | Active | OnHold | Completed | Dropped`, same set as Inkdrop) lives on the Note and is changed through the organization endpoint with the notebook, pin and tags (one request, one `Version` bump). The enum travels as its NAME in JSON (`[JsonConverter(JsonStringEnumConverter<NoteStatus>)]`) and is stored as text (`HasConversion<string>`, default `"None"`), so clients and database rows never depend on the enum's numbers. `IsInEnum()` rejects numbers outside the set. `status` is a required field of the organization request (not optional): a client that forgets it would otherwise silently reset every note to None.
- **Unreadable request bodies answer 400, not 500** – `BadRequestExceptionHandler` (an `IExceptionHandler`) maps `BadHttpRequestException` (malformed JSON, unknown enum name...) to a ProblemDetails 400 without echoing the exception message. Before, `UseExceptionHandler()` turned every such client mistake into a 500.
- **The editor looks like the preview while you type** – a CodeMirror ViewPlugin (`markdown-live-style.ts`) adds a CSS class to whole LINES from the Markdown syntax tree (headings h1-h6, quote, fenced/indented code, table, rule) and `HighlightStyle` styles the inline pieces (bold, italic, ~~strike~~, `code`, links). The Markdown marks (`#`, `*`) stay visible, in their own color: what you see is still exactly what is in the file (hiding marks off the active line, Obsidian-style, was left out on purpose: more code and cursor edge cases). Prose uses the same sans-serif font and line height as the preview; code and tables stay monospace so `|` columns line up.
- **The editor uses the GFM dialect** (`markdown({ base: markdownLanguage })`). The default of `@codemirror/lang-markdown` is plain CommonMark: tables and `~~strikethrough~~` were not even recognized in the editor before. It is also what the preview supports (remark-gfm).
- **No status line under the editor** ("All changes saved · Updated ... · Version n" removed at the user's request). Autosave failures still show a toast and the 409 banner; the one state that would otherwise be invisible, "too long to save", has its own error alert above the panes.
- **Edit/Split/Preview switch sits in the middle of the toolbar row** (grid `1fr auto 1fr`: the two outer columns are equal, so it is the true center), next to the notebook, status and tag pickers. The notebook picker has a search box (`nzShowSearch`, matches the full "Parent / Child" path); the tag picker (multiple mode) always has one. The tag picker is small and shows one chip plus "+N" so the row never grows taller.
- **The preview is ONE color; the editor is the colorful side** (user request, supersedes the earlier "preview and editor share the syntax colors"). `.markdown-body` uses `--ink-preview-text` for everything: headings, bold, italic, links, quotes, inline code, Shiki code blocks (its `--ink-code-*` variables are all pointed at that token inside `.markdown-body`) and Mermaid text/lines. Things are told apart by size, weight, underline (links) and backgrounds, not hue. Values: Light `#1c1f23`, Warm `#26231d` (near-black); **Dark uses its normal light text `#d8dee9`, because black on `#2e3440` would be unreadable**.
- **Sidebar rows carry their own actions, status and tags** – every row has small buttons (folder: new note, new subfolder, rename, "..."; note: rename, "...") that show on hover, on keyboard focus and ALWAYS on the open note and the current folder, so after a click the options are already there; the right-click menu stays and has the same entries. A note row also draws a second line with its status chip (colored dot + label, colors `--ink-status-*` in all three themes, contrast >= 4.5:1 on the sidebar) and at most two tag names plus a "+N" chip (tooltip lists them all). Names are bold (600).
- **Renaming a note = open it and focus its title** (`NotesStore.requestTitleFocus(id)` + an effect in the editor) instead of a rename dialog. The summary list has no content, so a dialog would need a GET + PUT that could race with the editor's autosave and overwrite a draft; the title is edited and saved in one place only. The request names the note id so a click on another, still loading, note cannot steal the focus. Enter in the title saves immediately.
- **Trash = the existing soft delete, made visible** – no new column: a note with `IsDeleted` IS in the trash, and `UpdatedAt` is the moment it was deleted. Endpoints live under `/api/notes/trash` (`GET` list, `GET /{id}` with content, `POST /{id}/restore`, `DELETE /{id}` for good, `DELETE` empty). Every trash query turns the soft-delete filter off (`IgnoreQueryFilters`) AND requires `IsDeleted`, so none of them can read or remove a live note (tested). "For good" and "empty" use one `ExecuteDeleteAsync` statement; the database removes the `note_tags` rows (cascade).
- **Restore** sets `IsDeleted = false`, `UpdatedAt = now` and bumps `Version` (a sync client must see the note as changed). Tags, pin, status and notebook come back with it; if its notebook was deleted meanwhile, the existing `ON DELETE SET NULL` already put the note in "no notebook". A note in the trash never blocks deleting its notebook (only live notes do).
- **Permanent deletion drops the row, so there is no tombstone** – fine while the app is single-device; Phase 7 (sync) must record permanent deletions somewhere (tombstone table) before a second device exists. No automatic purge after N days yet (not requested).
- **`TrashStore` is separate from `NotesStore`** so a deleted note can never appear in the sidebar by accident; the trash page asks `NotesStore.loadNotes()` after a restore, and the sidebar reloads the trash after a delete (for the count next to "Trash"). Only the irreversible actions (delete forever, empty) ask for confirmation; moving a note to the trash and restoring do not.
- **Outlined danger buttons use `--ink-danger`** (ng-zorro's own red is too dim on the dark theme); a plain `nz-button` has no `ant-btn-default` class, so the override uses a `:not()` list.
- **Phase 5 auth = ASP.NET Core Identity (users, password hashing, lockout) + our own JWTs** – `AddIdentityCore` (not the cookie sign-in of full Identity), the Guid-keyed `AppUser`, tables `users`, `user_claims`, `user_logins`, `user_tokens`, `refresh_tokens`. Password rule: minimum 8 characters, no composition rules (length protects more than "needs a symbol"), maximum 128 (hashing is slow on purpose). 5 wrong passwords lock the account for 15 minutes. Login answers the same 401 for a wrong password and an unknown email (and hashes anyway, so timing does not tell); register answers 409 for a taken email, which does reveal that the email exists (accepted: a registration form cannot avoid it without email verification, which comes later if ever).
- **Two tokens.** Access token: JWT HS256, 15 minutes, claims `sub`/`email`/`jti`, validated for issuer, audience, signature (only HS256 accepted), lifetime (30 s skew). It cannot be revoked once issued, hence short. Refresh token: 256 random bits, 30 days, stored only as a SHA-256 hash (`refresh_tokens.token_hash`, unique), ROTATED on every use inside a "family" (one sign-in). A rotated token used again after a 10 s grace (two tabs refreshing together) revokes the whole family (theft assumed); within the grace it is just refused. Rotation is one conditional `UPDATE ... WHERE revoked_at IS NULL`, so racing requests cannot both win. Logout revokes the family. `Jwt:Key` (>= 32 bytes) is a secret: user-secrets in development, environment variable in production; the app refuses to start without it (`ValidateOnStart`).
- **Where the browser keeps them.** Access token: in memory only (a signal), never in localStorage/sessionStorage, so injected script cannot read a long-lived copy. Refresh token: cookie `inknote_refresh`, `HttpOnly` (script cannot read it), `SameSite=Lax`, `Path=/api/auth` (not sent with note requests), `Secure` when the request is HTTPS. CORS now allows credentials (explicit origin only). A reload restores the session with one refresh call; a `localStorage` hint ("inknote.session", not a secret) lets first-time visitors skip that call. Cross-site cookie setups (front end and API on different sites) will need `SameSite=None; Secure` in the deployment phase.
- **Every endpoint requires sign-in by default** (fallback authorization policy). Open on purpose: `/api/health`, `/api/auth/*` (limited to 20 requests/minute per IP: register, login, refresh, logout share the limit), the OpenAPI document in development. A test calls every data endpoint without a token and expects 401.
- **Per-user data is filtered ONCE, in `AppDbContext`**: `UserId` on notes, notebooks and tags + global query filters `UserId = current user` (and `AND NOT is_deleted` for notes), where "current user" is `ICurrentUser` (the `sub` claim). With no user the filter matches nothing. The trash needs `IgnoreQueryFilters`, which would also drop the owner check, so it goes through `AppDbContext.TrashedNotes`, the only place that does both. Related ids sent by a client (notebook, tags) are checked through the same filtered sets, so another user's notebook/tag id simply "does not exist" (400/404). `NoteTag` has no owner of its own: it is reached only through an owned note and an owned tag. Tag names are unique per user (`unique(user_id, normalized_name)`); owners are `ON DELETE CASCADE`.
- **Legacy data**: rows that existed before accounts have `user_id NULL` (nobody can see them). The first account ever registered adopts them in one step (`ILegacyDataAdopter`, a no-op on a clean database); this is development convenience and can be removed once no pre-auth data exists. `UserId` stays nullable only for those rows; new rows always have one.
- **Signing out reloads the page** (`HARD_NAVIGATE`): the stores are app-wide singletons, and a full load guarantees that nothing of the previous user survives in memory. Same when the session cannot be renewed (the login page remembers `returnUrl`, and only paths inside the app are accepted from it, against open redirects).
- **Not done yet (on purpose)**: email confirmation, password reset, "sign out everywhere", cleanup of expired refresh tokens (rows accumulate; a periodic delete is easy later), social login. Passwords are hashed with Identity's default (PBKDF2, 100,000 iterations of SHA-512 in .NET 9).
- **"Keep me signed in" (remember me)** – a checkbox on the sign-in AND register forms, OFF by default (on a shared computer the safe choice must be the one nobody has to think about). The request carries `rememberMe` (missing = false). It is stored on the refresh token (`refresh_tokens.is_persistent`) and inherited by every token rotated from it, so a remembered sign-in stays remembered and a browser session stays a browser session. Remembered: cookie with an expiry date, server lifetime 30 days (sliding). Not remembered: a SESSION cookie (no expiry: the browser deletes it when it closes) and a server lifetime of 12 hours (sliding), which also ends sessions of browsers that are never closed and limits what a copied cookie is worth. The access token is unaffected (always 15 minutes, memory only). No absolute maximum age yet: a remembered sign-in that is used at least every 30 days never ends until sign-out. The migration gives existing rows `is_persistent = true` (they were all 30-day tokens); the MODEL has no default on purpose, because EF treats `false` as "not set" for a bool with a default and would silently store `true`.
- **Phase 6 search lives in the Notes module, not in a module of its own** – the search index IS columns and indexes of the `notes` table (a generated `tsvector`, three indexes), and a module may not touch another module's tables. Splitting would need a contract that exposes raw SQL, i.e. a module that is only a wrapper. It can be extracted when it has its own data (attachment text, for example). Endpoint: `GET /api/notes/search?q=&tagId=&notebookId=&page=&pageSize=` (page size 20, max 50, query 1..100 characters; 400 otherwise).
- **How a note matches.** Every WORD of the query must be satisfied (AND), and a word is satisfied by (1) a word of the note that STARTS WITH it, found through `search_vector` (generated column: `setweight(to_tsvector('simple', f_unaccent(title)),'A') || setweight(to_tsvector('simple', f_unaccent(content)),'B')`, GIN index), or (2) for words of 4+ letters, a SIMILAR word in the title or content (`pg_trgm` `<%` word similarity, two GIN expression indexes on `f_unaccent(lower(...))`). The typo test is per word: comparing the whole phrase made "alpha beta" find "alpha gamma" (a test caught it). `simple` configuration: PostgreSQL has no Vietnamese dictionary, but Vietnamese words are space-separated, which is all `simple` needs (no stemming, no stop words). `f_unaccent` is an IMMUTABLE SQL wrapper around `unaccent()` (which is only STABLE), required for a generated column and for indexes; it handles `đ`. Both extensions are "trusted" in PostgreSQL 13+, so no superuser is needed to create them.
- **Known limits of the typo tolerance** (measured, not guessed): one missing or extra letter in words of ~6+ letters is found ("meting", "progamming", "kubernets"); a swapped pair or a changed letter in a short word is not ("recieve", "budjet", "metting"); words under 4 letters are matched only by their beginning. The query can contain at most 10 words of 50 characters.
- **Ranking is deliberately cheap**: `ts_rank_cd` (words close together; title weighs more than content through the vector weights) plus 0.6 x trigram similarity of the title; ties go to the most recently edited note, then by id (a total order, so paging never repeats or skips a note). Comparing the query with the whole content in the score made a query that matches most of 20,000 notes take 2-6 s; without it, ~0.1 s. The page is found first (ids only), then the content of just those notes is read for the snippets. Measured on 20,000 notes: a rare word ~0.15 ms with the indexes (1305 ms without, 253 ms for `ILIKE '%word%'`).
- **Results contain no HTML.** Title and snippet are lists of `{text, match}` parts, computed in C# on the ORIGINAL text (the match is found in the unaccented text and mapped back to character positions, so "đường" is highlighted with its accents). The client draws matches with `<mark>`; `innerHTML` stays reserved for the sanitized Markdown preview. The snippet comes from the first 100,000 characters of the content (the index covers all of it).
- **The query lives in the URL (`?q=`)** like the tag filter: reload, Back and links keep it; opening a note keeps `q` so the results stay while reading. Typing is debounced (250 ms) and replaces the history entry (a letter must not be a Back step); the box follows the URL only when the change did not come from this component (otherwise a slow navigation could overwrite what was typed since). A search needs at least 2 characters; results are paged with "Show more" (the store drops answers to superseded queries and de-duplicates notes that move between pages).
- **Phase 7 local-first: the app reads and writes ONLY the local database.** Stores read IndexedDB through Dexie live queries (so a change from any source, including the sync, updates the screen) and every write goes to Dexie and to the outbox in ONE transaction. A sync engine pushes the outbox and pulls changes in the background. Only search and the trash still call the server directly (they need the server's index/data and are online-only on purpose). One database per user (`inknote-<userId>`).
- **Ids are chosen by the client** (GUIDs) so a note can be created offline and keep its id; the server accepts the id and refuses ids owned by another user. `version` 0 = never synchronized.
- **Sync protocol**: `POST /api/sync/push` (max 50 operations) and `GET /api/sync/pull?cursor=`. Operations are PATCHES (absent field = unchanged, `null` = clear), carry a client `opId` (`sync_operations` makes a retried push idempotent) and the `baseVersion` they were made on. Pull is ordered by a GLOBAL PostgreSQL sequence `sync_seq`, stamped by BEFORE INSERT/UPDATE triggers (so FK `SET NULL`, `ExecuteUpdate` and any future writer are covered without remembering to stamp) and deletions are recorded by AFTER DELETE triggers in `sync_tombstones`.
- **Settle window (default 2 s)**: a transaction that takes a lower sequence number can commit AFTER one that took a higher number, so a client could move its cursor past a change not yet visible and never see it. Pull therefore hands out only changes older than the window, and only the consistent prefix (it stops before the first change that is too young). Measured with the database clock. Cost: a change reaches other devices up to ~2 s later (+ the client's own timer).
- **Conflicts: last write wins, but nothing is lost.** A conflict = stale `baseVersion` AND the patch overwrites a differing title/content. Then the server text is saved as a `NoteRevision`, the client's patch wins and the answer is `conflict` (the user gets a notice). Changes to different fields (pin on one device, text on another) just merge. Revisions are readable through `GET /api/notes/{id}/revisions`; a screen for them comes in Phase 11.
- **Edge cases decided**: edit of a trashed note is applied to the trashed copy (`gone`, the user is told); edit of a purged note is `gone`; a notebook/tag deleted elsewhere is dropped from the patch; tag name clash becomes "name (2)"; deleting a not-empty notebook is `rejected` and the notebook is restored locally. Purging a note from the trash writes no tombstone (it was already reported deleted when it went to the trash).
- **Outbox rules**: at most two queued operations per thing: one `attempted` (handed to the network, so the server may have applied it: NEVER changed again, a retry must be identical for idempotency) and one `pending` (still mergeable, so a burst of typing is one operation). A pending operation that depends on an unanswered create (`awaitsBase`) is rebased with the confirmed version. Deleting something that never reached the server queues nothing.
- **Sync module owns no other module's tables**: Notes/Notebooks/Tags implement `ISyncHandler` (pull/apply for their own data) and Sync only orders, batches, stamps idempotency and decides statuses.
- **Sign-out wipes the local database** (a shared computer must not keep the notes). So it first tries to send what waits (max 4 s) and, if something still cannot go, asks for confirmation. A session that merely EXPIRES keeps the data. Data on the device is NOT encrypted (anyone with access to the browser profile can read it); end-to-end encryption is a later option.
- **Offline start**: the last user (id + email, no secrets) is cached in `localStorage` (`inknote.user`). A refresh that fails with a NETWORK error (status 0) neither ends nor renews the session; the app carries on from local data and the token is renewed by the interceptor on the first 401. Reloading the page while offline still needs the PWA service worker (Phase 9).
- **The notes page shows its inner pages (`router-outlet`) only after the local database is open** (`NotesPageComponent.ready`). Every inner page (editor...) assumes an open database; creating them earlier made a reload on `/notes/<id>` fail. If the database cannot be opened the page shows an error and nothing inside.
- **Why polling for now**: the engine pulls after local changes, every 30 s, when the tab becomes visible and when the browser reports "online". SignalR (Phase 8) will tell other devices to pull at once; the same pull is used.
- **Phase 8 real-time = a doorbell, not a second data channel.** The SignalR hub (`/hubs/sync`) only ever sends `changed`, with NO data. A device that hears it runs the normal pull from Phase 7. So there is one way for data to reach a device (security and conflict rules stay in one place), and a lost notification is harmless: after every (re)connection one synchronization catches up, and the 30 s timer remains as a safety net.
- **The notification is delayed by the settle window (+150 ms margin) and merged per user** (`SyncNotifier`). Telling a device at once would send it to pull while the new change is still younger than the settle window: it would get nothing and nothing would ring again. A burst of changes becomes ONE message (sent when things went quiet, and at least every 10 s). Cost: ~2.2 s between a change being saved and the other device being told.
- **Who rings it: an EF Core `SaveChangesInterceptor`, not calls sprinkled in services.** Whenever a note, notebook or tag is saved (sync push, REST endpoints, trash restore, FK-driven deletes through a tracked delete), the owner's devices are told. Same reasoning as the Phase 7 triggers: nobody can forget. Owners are collected before the save and announced only after it succeeded; a failed or rejected change tells nobody. Not covered on purpose: `ExecuteDelete` (purging the trash: other devices already treat that note as deleted) and token/adoption bulk updates.
- **Hub security**: `[Authorize]` + the fallback policy; the user id comes from the validated token (`sub`), the connection is put in the group `user:{id}` and groups drop it by themselves on disconnect. Clients call nothing on the hub, so there is no hub method to attack. A browser WebSocket cannot send an `Authorization` header, so SignalR sends `?access_token=`; the JWT middleware reads it ONLY for paths under `/hubs` (never for the REST API; a test checks this). A token in a URL can end up in proxy logs: acceptable because the access token lives 15 minutes and the hub is the only place it appears like that. An open connection is not re-checked when the token expires (it ends when the connection does); sign-out and the refresh-token rotation still apply to every new connection.
- **Reconnecting is done by `RealtimeSync`, not by SignalR's `withAutomaticReconnect`**: one mechanism, a fresh connection and a FRESH TOKEN for every attempt (the factory renews a token that is about to expire, found by reading its `exp`), pauses 0.5 / 1 / 2 / 5 / 10 / 30 s, an immediate try when the browser reports `online`, and a catch-up synchronization after every successful connection. Measured: after a server restart the devices reconnect on the first attempt after the server is up (up to 10-30 s with the longest pauses); changes made meanwhile are queued and sent after reconnecting. SignalR's own log is off (`LogLevel.None`); the browser itself may still print "WebSocket connection failed" lines while the server is down.
- **Deliberate simplification**: the device that made a change also gets the notification and pulls once more (one cheap extra request). Excluding it would need the connection id on every push request; do it only if this ever matters. The 30 s timer was not lengthened while the hub is live (it costs one small request).
